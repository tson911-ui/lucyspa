## Services pagination: what the design says

- **D6** (Owner decision): "Every list has pagination (plus search/filters where useful)."
- **10.2**: every list uses `ListToolbar` + `DataTable` + `Pagination`, page size 20, search when rows can exceed ~15, URL params `q`, filters, `page`, `pageSize`.
- **Q-D3** (locked): lists whose API is not paginated paginate in the browser over the loaded set (20 per page); server paging only where it exists or volume demands.
- **3 (inventory)** records Services as "grouped by category, unpaged", template List+detail; migration belongs to **Step 9** (Catalog and Sales: services +
  detail, branches, discounts, POS), not yet done. Steps 4 (Employees, Skills pilots) and 7 did not touch it.

## Proposal (not started)

1. Bring the Services list forward as its own small Step (9a) instead of waiting for all of Step 9: `DataTable` in client mode (20 per page, sort by code, name, category, price), `ListToolbar` with search (code, VI/EN name), category and status filters, `role="status"` count, URL state; price right-aligned, `nowrap`, tabular digits; phone card list via `mobileTitle`/`mobileMeta`.
2. Replace category grouping with a category column + filter; categories become a second tab ("Nhóm dịch vụ", max 10 rows, paginated beyond 20).
3. Row actions via `RowActions`: Edit, then a `...` menu with Delete/Deactivate per 10.4-10.5 (no stacked text link + outlined button).
4. No API change (the endpoint returns all services; 64 rows is fine client-side). Reuse the same component set for Branches, Teams and Discounts in the same Step.
5. Separately, a short "consistency" Step before 8-10 would remove findings 1, 5, 6 centrally: one card (`Card`) for `Section`, empty/notice/table without their own border inside a card, `.wf-app` base font and legacy paddings mapped to tokens.

Owner decision needed: take 9a + the consistency Step now (recommended), or continue with Step 8 and fix these inside Steps 8-10.
